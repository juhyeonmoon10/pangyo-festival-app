# NFC 서버 설치안 검토 (2026-09-10)

검토 대상: `install.sql` (176줄), `database-rollback.sql`, 새로 작성한 `disable.sql`, `uninstall.sql`, `precheck.sql`.
검토 방식: SQL 원문 읽기, ORBIT 저장소 읽기 전용 확인, 격리된 PGlite 데이터베이스에서 실행 검증.
이 문서를 쓰는 동안 공용 Supabase 프로젝트(`vvvkzvxahviwbuyfbwir`)에는 어떤 조회나 변경도 하지 않았다.
ORBIT 저장소·팀 파일도 수정하지 않았다.

## 1. 결론 요약

- `install.sql`은 새 테이블을 만들지 않지만 **기존 `public.users`의 조회·수정 권한을 좁힌다.** 이 부분이 다른 팀에 영향을 줄 수 있는 유일한 변경이다.
- 격리 환경에서 설치 → 동작 → 중지 → 제거 → 재설치까지 27개 검사가 모두 통과했다. 설치 SQL 자체의 논리 결함은 찾지 못했다.
- 그러나 격리 환경은 Supabase Vault 암호화, GoTrue 세션 발급, PostgREST 전송, 동시 접속을 흉내 내지 못한다. 공용 서버 적용 전에 `precheck.sql`(읽기 전용)로 현재 상태가 2026-09-09 관찰값과 같은지 반드시 재확인해야 한다.
- 복구 수단은 두 단계로 준비했다. `disable.sql`은 학생 RPC 호출만 즉시 막고, `uninstall.sql`은 함수·스키마·비밀을 제거하고 9월 9일 권한으로 되돌린다. 둘 다 적립된 `completed_booths` 데이터는 지우지 않는다.
- 4단계(관리자 화면에서 태그 발급)는 현재 SQL에 **없는** 관리자용 발급 RPC가 추가로 필요하다. 별도 설계·승인 항목이다.

## 3. 다른 팀에 미치는 영향 분석

### 3.1 영향을 받는 코드 유형

1. **학생 세션으로 `users`를 직접 UPDATE** (`supabase.from('users').update(...)`): 설치 후 실패한다. 예: 브라우저에서 돈·완료 부스·관리자 플래그를 직접 바꾸는 코드.
2. **학생 세션으로 다른 사용자 행을 SELECT**: 결과가 본인 행 1건으로 줄어든다. 예: 브라우저에서 `users`를 직접 읽어 랭킹이나 사용자 목록을 만드는 코드.
3. **`users`를 참조하는 다른 테이블의 RLS 정책**: 정책 본문이 "본인 행"만 필요로 하면 계속 동작한다. 9월 9일 관찰된 `booth_ratings_own_insert`는 이메일 연결을 검사한다고 기록돼 있는데, 본문이 다른 사용자 행을 봐야 하는 형태라면 리뷰 등록이 막힐 수 있다. `precheck.sql` 3번 조회로 본문을 확인해야 한다.

### 3.2 영향을 받지 않는 코드 유형

- `SECURITY DEFINER` 함수(소유자 postgres)와 service_role 키를 쓰는 서버 코드. RLS와 grant 회수 모두 우회한다.
- Supabase Auth 가입 트리거처럼 postgres 권한으로 실행되는 트리거.
- `booths` 공개 조회, `booth_ratings` 조회 등 `users` 정책과 무관한 접근.

### 격리 환경이 증명하지 못하는 것

- Supabase Vault의 실제 암호화·`vault.create_secret` 시그니처 차이. 실제 DB에서는 9월 9일 초기 후보가 이미 트랜잭션 안에서 성공했으므로 위험은 낮지만, 강화판은 재실행이 필요하다.
- GoTrue가 발급하는 JWT의 `session_id` 클레임 존재와 `auth.sessions.not_after` 갱신 방식. Supabase는 refresh 시 세션 행을 유지하지만, 이 검사는 실제 로그인으로만 확정된다.
- 여러 세션이 동시에 같은 사용자로 적립할 때의 잠금 동작(단일 연결이라 검증 불가).
- 실제 Google OAuth, 실물 카드, PostgREST 오류 코드 매핑.

## 5. 복구 방법

| 상황 | 조치 | 남는 것 |
| --- | --- | --- |
| 적립 오류·악용 의심, 즉시 중단 | `disable.sql` 실행. authenticated의 RPC 실행 권한 회수 + Vault `enabled=false` | 정책·함수·데이터 그대로. 재개는 `grant execute` 복구와 `enabled=true` |

| 설치 자체 실패 | 트랜잭션이라 부분 적용 없음. 오류 메시지의 사전 검사 이름으로 원인 판단 | 변경 없음 |

주의: `uninstall.sql`은 `users_authenticated_select/update`를 9월 9일 관찰값(전체 조회·전체 수정 허용)으로 되돌린다. 이것은 원래 보안 우려였던 상태이므로 **자동 실행하지 않고 운영자가 판단해서** 실행한다. `nfc-server/README.md`의 "문제가 생기면 NFC 함수 실행을 제한" 원칙과 같다.

## 6. 공용 서버 적용 전 승인 요청 항목 (3단계용)

아래 각 항목에 대해 이번 변경에 한정한 명시적 승인이 필요하다.

1. **읽기 전용 사전 점검** `precheck.sql` 실행. 정책 이름·본문, users 컬럼 목록, `booth_ratings` 정책 본문, Vault 권한, `festival_nfc_private` 부재 확인. 9월 9일 값과 다르면 적용을 멈추고 다시 검토한다.
2. **재검증 트랜잭션**: `install.sql`의 마지막 `commit;`을 `database-rollback.sql`로 바꿔 실제 DB에서 한 번 실행. 결과가 PASS 문자열이고 `festival_nfc_private`가 없어야 한다. SQL Editor에 붙여 넣을 때 `$$`가 깨지면 RLS 경고가 나므로 파일 내용을 그대로 붙여 넣고, 경고를 우회하지 않는다.
3. **설치**: `install.sql` 그대로 실행. 직후 `precheck.sql`을 다시 실행해 정책이 본인 행 조회·UPDATE 거부로 바뀌었는지, anon 실행 거부인지 확인.
4. **Auth URL 설정**: 기존 Site URL과 ORBIT redirect 2개를 그대로 두고 `pangyofestival://auth/callback` 한 줄만 추가. 웹 복귀 주소는 공개 배포 주소가 확정된 뒤 별도 승인.
5. **태그 발급**: 운영자가 SQL 권한으로 `festival_nfc_private.issue_tag('<부스 enum>', now() + interval '...')` 호출. 유효기간 최대 7일. 발급 토큰은 채팅·문서·Git에 남기지 않는다.

## 7. 추가로 확인된 사실과 개선 후보

- 서명 URL `pangyofestival://nfc#t=<토큰>`은 **276바이트**(토큰 253자). NTAG213(사용 가능 약 144바이트)에는 들어가지 않고 NTAG215(약 504바이트) 이상이 필요하다. Android `NfcUrlPolicy`는 8192자까지 허용하므로 앱 쪽 제한은 없다.
- 부스 태그는 학생 간 공유가 전제다(같은 태그로 여러 학생 적립). 태그 URL 복사·공유를 막지는 못한다. 기존 README와 같은 한계다.
- 형식은 맞지만 payload가 깨진 토큰(enum에 없는 부스, expires 누락)도 `NFC_TAG_EXPIRED`로 응답한다. 안전하지만 메시지가 정확하지 않다. 바꾸려면 SQL 수정·재검증이 필요하므로 이번 승인 범위에서는 그대로 둔다.
- 적립 RPC에 호출 빈도 제한이 없다. 5분 내 과다 방문 제재는 원래 미구현 항목이다.
- `issue_tag`는 SECURITY INVOKER라서 Vault를 읽을 수 있는 역할(postgres)만 발급할 수 있다. **관리자 화면에서 발급하려면 `users.admin`을 검사하는 SECURITY DEFINER 발급 RPC를 새로 추가해야 하며, 이것은 현재 `install.sql`에 없다.** 4단계 전에 별도 설계와 승인이 필요하다.

## 7.1 관리자 발급 RPC 초안 (`admin-issue.sql`, 같은 날 추가)

4단계를 위해 `install.sql` 뒤에 따로 적용하는 파일이다. 테이블·컬럼·정책은 바꾸지 않고 함수 두 개만 추가한다.

| 항목 | 내용 |
| --- | --- |
| 공개 RPC | `public.festival_nfc_admin_issue(p_booth text, p_valid_minutes integer)` → `{token, boothKey, expiresAt, issuedAt, validMinutes}` |
| 권한 판정 | `festival_nfc_private.current_profile()`로 Google·이메일 인증·세션 검사를 통과한 뒤, **본인 `public.users` 행의 `admin = true`** 일 때만 발급. Auth metadata나 클라이언트 값은 사용하지 않는다. `admin` 플래그는 앱이 켤 수 없고 팀이 DB에서 지정한다. |
| 입력 제한 | 유효기간 1~10080분(7일), 부스는 `public.booths`에 있는 enum 값만. 위반 시 `INVALID_TAG_ISSUE_REQUEST` / `NFC_TAG_INVALID` |
| 실패 코드 | 비관리자 `ADMIN_REQUIRED`(42501), 로그인 문제 `AUTH_REQUIRED`/`GOOGLE_AUTH_REQUIRED`, Vault 꺼짐 `NFC_DISABLED` |
| 실행 방식 | SECURITY DEFINER로 기존 `issue_tag`를 호출한다. 관리자도 Vault를 직접 읽을 수는 없다. |
| 사전 검사 | `install.sql` 미적용이면 `NFC_INSTALL_REQUIRED_FIRST`, 이미 있으면 `..._ALREADY_INSTALLED_...`로 거부, `users.admin` boolean 컬럼 필요 |
| 복구 | `disable.sql`이 이 RPC의 실행 권한도 함께 회수(함수가 없으면 건너뜀). `uninstall.sql`이 공개 래퍼를 제거 |

격리 검증(phase G, 7개 검사)에서 확인한 것: 적용·중복 적용 거부, anon·일반 학생·행 없는 계정·세션 없는 계정 거부, 팀이 `admin=true`로 지정한 계정만 발급, 발급 토큰을 다른 학생이 적립(`EARNED`)하고 재태깅 시 `ALREADY_EARNED`, 유효기간 경계값(0·10081·null 거부, 1·10080 허용), 없는 부스 거부, Vault 꺼짐·세션 만료 시 발급 거부, epoch 교체 시 발급 토큰 무효, `disable.sql`/`uninstall.sql` 연동, 미설치 DB에 단독 적용 시 흔적 없이 거부. 전체 34/34 통과.

남은 한계: 발급 이력·횟수 기록이 없다(새 테이블 필요). 관리자 세션이 탈취되면 7일짜리 토큰을 만들 수 있으므로 행사 당일에는 짧은 유효기간을 쓰고, 문제가 생기면 `epoch`를 교체한다. 클라이언트(`festival-account.js`, NFC 관리 화면) 연결은 아직 하지 않았다.

## 9. 2026-09-11 추가: 별점·후기 SQL과 프로필 변경

`install.sql`의 프로필 응답에 `isAdmin` 한 필드를 추가했다. 호출자 **본인** `users.admin` 값이며
권한을 부여하지 않는다. 모든 운영자 동작은 서버에서 다시 검사한다. `money`는 여전히 응답에 없다.

`reviews.sql`은 기존 `public.booth_ratings`를 사용한다.

- 추가되는 스키마 변경은 nullable 컬럼 `content` 하나와 500자 길이 제약뿐이다. 다른 코드의
  기존 insert는 그대로 동작한다.
- `festival_review_submit`은 별점 1~5, 500자 이하 글, **서버에 기록된 방문**을 확인한 뒤에만
  저장한다. 같은 부스 재작성은 `ALREADY_REVIEWED`로 거부한다.
- `festival_booth_reviews`는 평균·개수·내 별점과 최근 50건을 돌려준다. 다른 학생 이름은 첫
  글자만 남기고 `○`으로 가린다(`김○○`). `public.users.name`을 원본으로 쓰며 auth 메타데이터는
  읽지 않는다.
- `festival_my_reviews`는 내가 별점을 남긴 부스 목록만 돌려준다. 홈의 "별점을 기다리는 부스"
  개수를 부스마다 요청하지 않고 계산하기 위한 것이다.
- `booths.rating`은 **건드리지 않는다.** 다른 팀의 집계 로직과 충돌하지 않도록 평균은 조회할
  때마다 `booth_ratings`에서 계산한다.
- 기존 `booth_ratings` insert 정책은 방문 여부를 검사하지 않으므로 브라우저에서 직접 별점을
  넣는 우회가 여전히 가능하다. 이를 막는 `revoke`문을 파일 끝에 주석으로 넣어 두었다. 다른 팀
  코드를 깨뜨릴 수 있으므로 팀과 합의한 뒤에만 해제한다.

격리 검증은 41개 검사로 늘었고 전부 통과했다. 추가된 항목은 설치·중복 적용 거부, 미방문 거부,
프로필 미등록 거부, 익명 거부, 별점만/글 포함 저장, 중복 작성 거부, 평균 계산, 이름 마스킹,
경계값, 내 목록, 그리고 `uninstall.sql` 후에도 저장된 후기가 남는지다.

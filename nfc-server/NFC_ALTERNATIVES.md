# NFC 방식 비교: URL 태그 대신 쓸 수 있는 것

작성일: 2026-09-11. 개인 앱(Android WebView + Reader Mode, Supabase RPC) 기준으로 조사했다.
코드, 공용 DB, ORBIT 저장소는 변경하지 않았다.

## 현재 방식 요약

- 카드(NTAG21x)에 NDEF **URI 레코드** `pangyofestival://nfc#t=<서명 토큰>`을 써 둔다.
- 앱이 꺼져 있으면 Android가 URI를 보고 앱을 실행하고, 켜져 있으면 Reader Mode로 읽는다.
- 서버는 HMAC 서명·만료·세대(epoch)·부스 존재를 검사한다.
- 한계: URL을 사진으로 찍거나 복사해 다른 사람에게 보내면 현장에 없어도 적립된다. 서명은 위조만 막고 복제·공유는 못 막는다.

"URL 말고"라는 요구는 두 가지로 나뉜다.
(1) 카드에 URL 형식 대신 다른 레코드를 쓰는 것. 보안은 그대로다.
(2) 복제·공유 자체를 막는 구조로 바꾸는 것. 카드 종류나 운영 방식이 바뀐다.

| A. 현재: 서명 URL | URI 레코드 | 없음 (위조만 방지) | 없음 | install.sql | NTAG215 이상, 약 수백 원 |
| B. 비URL NDEF 레코드 + AAR | 외부 타입 레코드(`pangyo.kr:stamp`)에 토큰, 앱 지정 레코드 | 없음 (A와 동일) | 네이티브 소량 | 없음 | A와 동일 |
| C. 칩 일련번호(UID) | 아무것도 안 씀. 7바이트 UID만 사용 | **약함**. UID 변경 가능한 복제 칩이 시중에 있음 | 네이티브 소량 | UID→부스 대응표 필요 (새 테이블 또는 Vault JSON) | 아무 NTAG, 가장 쌈 |
| D. NTAG 424 DNA (SUN) | 탭할 때마다 칩이 만드는 일회성 코드(암호화 UID + 카운터 + CMAC) | **강함**. 칩 안의 AES 키가 있어야 다음 코드를 만들 수 있음. 코드 재사용은 카운터로 탐지 | 없음 (URL 형태로도 됨) 또는 소량 | AES-CMAC 검증 로직 + 카드별 키 보관 | 개당 약 0.5~1 유로(1000개 기준), 국내 소량 구매는 더 비쌈. 전용 인코딩 도구 필요 |
| E. 부스 폰이 카드 역할 (HCE) | 카드 없음. 부스 운영자 폰이 탭마다 새 서명 코드 생성 | **강함**. 부스 폰이 그 자리에 있어야 함 | 네이티브 중간 (IsoDep 읽기 + 부스 모드 HCE 서비스) | 부스별 키 발급 RPC 또는 온라인 검증 | 부스마다 Android 폰 1대 + 운영자 |
| F. 학생 폰이 카드 역할, 부스가 찍음 | 카드 없음. 학생 앱이 HCE로 학생 토큰 제시, 운영자 폰이 읽어 서버에 기록 | **강함**. 운영자가 눈앞의 학생만 기록 | 네이티브 중간 (양쪽 모드) | 운영자 권한 RPC (`admin` 또는 부스 담당 역할) | 부스마다 Android 폰 1대 + 운영자 |
| G. 비밀번호 보호 영역 읽기 | NTAG 비밀번호(PWD_AUTH) 뒤에 숨긴 값 | 약함. 비밀번호가 APK 안에 있음 | 네이티브 | 없음 | NTAG21x |

## 각 방식 설명

### B. 비URL NDEF 레코드 + Android Application Record

- URI 대신 **외부 타입 레코드**(예: `pangyo.kr:stamp`) 안에 토큰만 넣고, 두 번째 레코드로 **AAR**(`android.com:pkg` = `com.juhyeonmoon.pangyofestival`)을 붙인다.
- 효과: 앱이 없는 폰에서 탭해도 브라우저가 열리지 않고 Play 스토어(또는 아무 일도 없음)로 간다. 카드 내용이 "링크"로 보이지 않는다. 토큰 앞의 `pangyofestival://nfc#t=` 22바이트가 줄어 NTAG213(144바이트)에도 253자 토큰이 **아슬아슬하게 못 들어간다**. NTAG215는 여전히 필요.
- 보안은 A와 같다. 토큰을 읽어 다른 카드에 그대로 쓰면 똑같이 적립된다.
- 변경: 매니페스트 필터 1개, `readMessage`에서 외부 타입 파싱, `NfcUrlPolicy` 대응. 서버·SQL은 그대로.

### C. UID만 사용

- 카드에 아무것도 쓰지 않고, Reader Mode의 `tag.getId()`(7바이트)를 부스에 대응시킨다.
- 장점: 카드 쓰기 작업이 없고 만료 개념도 없다.
- 단점: "UID 변경 가능(magic)" NTAG213/215/216이 연구용으로 흔히 팔린다. UID를 읽는 앱은 누구나 쓸 수 있으므로 복제 카드 제작이 쉽다. 또 UID→부스 대응표를 서버에 둬야 하는데 새 테이블이 필요하다(승인 사항). 대응표를 Vault JSON에 넣는 편법은 운영 변경 때마다 비밀을 고쳐야 해서 권하지 않는다.
- 결론: 현재 서명 방식보다 나쁘다.

### D. NTAG 424 DNA와 SUN(Secure Unique NFC)

- 칩 안에 AES-128 키가 들어 있고, 탭할 때마다 칩이 **암호화된 UID + 읽기 카운터 + CMAC**을 NDEF 데이터에 직접 써서 내보낸다. 같은 데이터가 두 번 나오지 않는다.
- 서버는 카드 키로 CMAC을 검증하고, 카운터가 이전보다 커졌는지 확인한다. 복사한 코드는 카운터 검사에서 걸리고, 새 코드는 진짜 칩 없이는 만들 수 없다.
- 보통 URL 안에 넣어 쓰지만, 우리 앱은 NDEF 파일을 직접 읽으므로 URL이 아닌 형식으로도 가능하다.
- 필요한 것:
  1. 카드별 키를 마스터 키에서 유도해 카드에 기록하는 **인코딩 작업**(NXP TagWriter 앱 또는 별도 도구). 일반 NFC Tools로는 SDM 설정이 안 된다.
  2. 서버의 **AES-CBC 복호화 + AES-CMAC 검증** 코드. pgcrypto에는 CMAC이 없어 plpgsql로 직접 구현하거나(수백 줄, 검증 부담), Supabase Edge Function(새 자원, 승인 필요)으로 만들어야 한다.
  3. 카드별 **마지막 카운터 저장**. 새 테이블 또는 기존 컬럼이 필요하다(승인 사항).
  4. 카드 단가 상승과 소량 구매 경로 확보.
- 결론: 카드로 복제를 막는 정석. 다만 20개 부스 규모의 교내 행사에서 서버 구현 난도와 승인 항목이 가장 많다.

### E. 부스 폰 HCE (부스가 카드 역할)

- 각 부스에 Android 폰 1대를 두고, 우리 APK의 "부스 모드"가 `HostApduService`로 카드처럼 동작한다. 학생 폰이 IsoDep로 접속하면 부스 폰이 **그 순간 서명한 일회성 토큰**(부스, 시각, nonce)을 돌려준다.
- 학생 앱은 받은 토큰을 지금과 같은 `festival_nfc_claim`으로 보낸다. 서버 SQL은 "nonce 재사용 금지"만 추가하면 된다(nonce 기록 위치가 필요하므로 이 부분은 승인 사항).
- 부스 폰의 서명 키: 관리자 발급 RPC로 부스별 단기 키를 받아 폰에 보관. 지금 만든 `admin-issue.sql` 구조와 잘 맞는다.
- 장점: 카드 구매·기록이 없다. 토큰이 매번 달라 공유가 무의미하다. 부스 폰이 꺼지면 적립이 멈추므로 운영 통제가 쉽다.
- 단점: 부스마다 폰과 담당자가 있어야 한다. Android 폰끼리 HCE 접촉은 화면이 켜져 있어야 하고 폰 케이스·안테나 위치 때문에 카드보다 접촉 실패가 잦다. 양쪽 모두 Android여야 한다.

### F. 학생 폰 HCE, 부스 운영자가 찍음

- E의 반대 방향. 학생 앱이 HCE로 "학생 토큰"을 제시하고, 운영자 폰(부스 모드)이 읽어 서버에 "부스 X에 학생 Y 방문"을 기록한다.
- 팀 ADR의 "운영자 수동 승인" 모델과 가장 가깝다. 운영자가 눈앞의 학생만 찍으므로 공유 문제가 원천 차단된다.
- 필요한 것: 운영자 권한(현재 `users.admin` 하나뿐, 부스별 담당 역할 없음)과 "다른 학생의 완료 배열에 추가"하는 RPC. 지금 SQL은 본인 행만 갱신하므로 새 함수·감사 기록이 필요하다(승인 사항).
- 단점: E와 같은 장비·인력 조건. 학생 폰 화면이 켜져 있어야 한다.

## 권장 순서

1. **지금 행사 규모(교내, 부스 20개, 보상 간식)에서는 A(현재 서명 URL) 또는 B로 충분하다.** 공유가 걱정되면 유효기간을 몇 시간으로 짧게 하고, 비정상 패턴은 관리자가 검토하는 기존 정책을 유지한다.
2. 카드 내용이 "링크"로 보이는 것이 싫거나 앱 미설치 폰에서 브라우저가 열리는 것을 막고 싶으면 **B**를 적용한다. 네이티브 소량 변경이고 서버는 그대로다.
3. 복제·공유를 기술적으로 막아야 한다면 **E(부스 폰 HCE)** 가 우리 구조에서 가장 현실적이다. 서버 변경이 가장 적고 `admin-issue.sql`을 그대로 활용한다. 부스마다 폰과 담당자가 있는지가 결정 조건이다.
4. **D(NTAG 424 DNA)** 는 카드만으로 해결하는 유일한 방법이지만 서버 암호 구현과 카운터 저장 테이블, 카드 인코딩 도구가 추가로 필요하다. 다음 행사나 규모가 커질 때 검토한다.
5. **C(UID)** 는 권하지 않는다.

## 어느 쪽이든 바뀌지 않는 것

- 로그인·프로필·본인 행 적립 RPC 구조는 그대로 쓸 수 있다.
- 새 테이블·컬럼·Edge Function이 필요한 항목은 전부 별도 승인 대상이다.
- iPhone은 어떤 방식이든 이 앱을 설치할 수 없다. 운영자 수동 승인이 대체 경로다.
- 실물 검증(RF 접촉, 제조사별 차이)은 어떤 방식이든 실기기로 해야 한다.
